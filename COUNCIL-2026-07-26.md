## 2. Still OPEN — ranked. Start a fix session here.

### HIGH

**H1 — Whole-document read-modify-write with no locking, and prefetch made it likely.**
`storage.py` `replace_one` has no version field, no CAS, no lock; gunicorn runs
2 workers × 4 threads. The new prefetch widened the race from milliseconds to a minute:
`GET /api/lesson/<day>` loads state → blocks on Gemini 15–60s → the user completes a
day/submits a quiz meanwhile → the prefetch saves **the state it read a minute ago**,
erasing XP, streak, `progress[day].completed`, quiz results, DNA. The user sees a
completed day un-complete itself. `save_notifications_for` (`storage.py`) is the one
place that got this right, with a surgical `$set`. **This is the most important
remaining bug.** Fix = per-endpoint `$set`, or a `rev` field with optimistic concurrency.

**H2 — Every daily boundary is UTC; rolls over at 05:30 IST.** `_today()` and
`_bump_streak`. A 22:00 IST Monday and a 00:30 IST Tuesday session are the *same UTC
day*, so Tuesday earns no streak credit; skip Tuesday daytime and Wednesday sees
`gap == 2` and **breaks a streak built from two real consecutive days**. Also affects
the warm-up XP guard, focus cap, and pace-check. The fix is already half-built:
`app.js` sends `getTimezoneOffset()` and `_bump_streak` accepts an injectable
`today_date` that no caller passes.

**H3 — Neither generation path validates day numbers against phase boundaries.** Shape
guards only check `isinstance(d["day"], int)`. If two phases both emit `day: 12`,
`progress["12"]`/`lessons["12"]` are single-keyed (completing one completes both) and
`project_id "p12"` collides. The parallel path (the only one the UI uses) is more
exposed — phases are generated in isolation. Correct numbers are already computable
from phase offsets.

**H4 — Starting a new plan erases the permanent best streak.** `plan_init` resets
`streak` without `best`, contradicting both the v13 migration comment and the
`_bump_streak` docstring. `lifetime_xp` on the adjacent line is preserved correctly;
`best` should match.

### MEDIUM

- **M1** Sign-out/401 leave the history stack pointing at the previous session's
  rendered DOM. Partly mitigated in `509d998` (401 now nulls `state`/`currentView`);
  the stale entries themselves remain.
- **M2** `prefetchTried.delete()` on failure → retry storm. `renderDashboard()` runs on
  every back-navigation, so a failing/quota-exhausted Gemini re-fires a 15–60s
  generation on every return to the dashboard.
- **M3** `_sanitize_phases` never pads an undershoot and can't trim when phase count >
  day count (8 phases for a 5-day ask → 8 days). Arithmetic stays self-consistent
  (`plan["days"]` is re-derived from the sum) — the damage is honesty, silently.
- **M4** `_wants_project`: the `is_last and n >= 2` clause is unreachable for a
  *compliant* 2-day final phase (the `teaching_left >= 2` guard needs ≥3 days), so it
  only fires when the model overshot. Also `idx < 1` means a single-phase plan silently
  gets zero projects.
- **M5** Push notifications fire at 00:30 IST for migrated users — the migration's
  `notifications` default omits `tz_offset`, and `push.py` falls back to 0.
- **M6** Saved-section bookmarks store `sectionIndex` and never use it — the row opens
  the lesson at the resume step instead of the saved section. Half-finished.
- **M7** Per-request document cost: every API call reads and rewrites the whole
  document; `VISUAL_RULES` allows unlimited inline SVG, so a 50-day plan plausibly
  reaches 5–8 MB. A bookmark tap moves that both ways on Atlas M0. `bookmarks` and
  `awarded` grow unbounded.
- **M8** Schema downgrade is silent and permanent (deploy 17 → roll back to 16 → docs
  keep `schema: 17` and never re-migrate).

### LOW
Dead `/api/plan/generate-phase` route (no callers); `renderDiagrams` touching a removed
node; two rapid `show()` calls letting one transition strip `html.vt` early; a failed
`openLesson` pushing two history entries; `renderDashboard` via popstate with no plan
throwing; material upload bypassing `api()` (no 401 handling, no `X-Requested-With`);
naive timestamps rendering a day early in IST; `sw.js` offline cache only refreshed when
`sw.js` itself changes.

## 4. Google / Gmail sign-in — the design, and the disagreement

The owner asked to replace name+password with Google sign-in ("passwords are a drag,
people forget them"). **The two agents that looked at it disagreed on whether to do it,
but agreed completely on how.**

### Where they agree (this part is settled)
- **It is technically feasible.** A TWA is *real Chrome*, not a WebView, so Google's
  embedded-webview ban does not apply; it shares Chrome's cookie jar, so signing in is
  usually one tap on an account already present. Use the **server-side authorization-code
  redirect flow**, NOT the GIS JavaScript button (popups in a TWA are untested, and it
  adds an external script to a PWA cold-start path).
- **Zero Android changes.** `/.well-known/assetlinks.json` already exists, which is what
  restores full-screen after the redirect. No new APK.
- **Zero new dependencies** — one `urllib` POST; Google explicitly permits skipping
  signature verification when the token comes straight from the token endpoint over
  HTTPS with the client secret (still assert `iss` and `aud`).
- **The uid must NEVER change.** Google identity is *linked onto* the existing account:
  add `google_sub` to the `users` doc and look the uid up from it. `storage.snapshot()`
  keys backups `f"{uid}__backup"`, so re-keying orphans the only backup — this trap is
  documented and has already fired once (see §5).
- **Keep password login permanently**, as a visible control. It is how the first link is
  performed, and the only way back in if Google fails.
- **`SESSION_COOKIE_SAMESITE="Lax"` is compatible** with a top-level GET callback — but
  would break instantly and confusingly under `Strict`. Comment the line.
- Store `sub`, never email (emails change and Workspace addresses get recycled).
- Google-created uids need a `g_` prefix, **not `g:`** — a colon is an illegal Windows
  filename character and local dev writes `mentoros_data/<uid>.json`.

### Where they disagree
**Architect: GO** (7–10h, with an abandon checkpoint after "proof of life" — see below).
**Red team: NO-GO on replacing passwords**, arguing the problem doesn't exist yet:
`session.permanent` + a 365-day lifetime + a Mongo-persisted `SECRET_KEY` means the owner
stays signed in for longer than the bootcamp lasts. It trades one self-serviceable
failure (forgot password, fixable from his laptop) for several externally-controlled ones
(consent screen expiry, test-mode 7-day token expiry, revoked client, Google outage,
college Wi-Fi) — none fixable from the phone. It also puts an "unverified app" warning in
front of classmates, and adds a cross-origin round trip to the cold-open that was just
optimised.

**Red team's cheaper alternative:** a `reset_password.py` sibling to `backup.py` (~15
lines, offline, zero production surface) plus optionally a one-time recovery code at
signup. That solves the stated problem entirely.

### If it is built anyway — the conditions
- [ ] Additive only: password login stays as a visible, permanent control.
- [ ] Google identity is a **link**, never a source of a new `_id`.
- [ ] `backup.py` also dumps the **`users`** and **`config`** collections (today it dumps
      only `state`, so any migration touching `users` has zero rollback), and a fresh
      backup is copied off the laptop first.
- [ ] `reset_password.py` exists and has been run once.
- [ ] Shipped **alone**, after the queued commits are verified live.
- [ ] `GOOGLE_CLIENT_ID` declared in `render.yaml` with `sync: false`.
- [ ] Tested on the real phone with a deliberate failure injected, confirming the
      password fallback rescues him.

**Abandon checkpoint (architect's, and it's good):** build only `/start` + `/callback`
where the callback logs the `sub` and redirects — no session write, no Mongo write, no UI
change. If the `sub` appears in the Render logs, everything after is easy. If not,
`git revert` and the app is byte-identical.

**Faiz's own steps** (Google Cloud Console, ~25 min) are in the architect's report:
project → Google Auth Platform → External → **only** `openid`, `email`, `profile` scopes
(any other scope triggers a multi-week verification review) → **Web application** client
type (not Android) → redirect URI `https://mentoros-c4ht.onrender.com/api/auth/google/callback`
byte-exact → `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` on Render.

## 5. Data discovery: the `default` doc is orphaned

The backup revealed three documents:

```
default              50 days, schema 12, 577 XP, 2 days done, streak 1   <- ORPHANED
faiz ahmed           40 days, schema 16,   0 XP, 0 days done             <- live account
faiz ahmed__backup   50 days, reason="reset", saved 2026-07-18           <- the ABANDONED plan
```

`LEGACY_OWNER` defaults to `"faiz"` but the real uid is `"faiz ahmed"`, so
`claim_legacy_state()` never matched. `default` is still at **schema 12** while the live
doc is at 16 — proof it was never loaded through `_migrate()`. **The owner's only real
usage history is unreachable by any code path.** Not urgent (the XP was inflated by the
old pace-check bug anyway), but it's the uid trap firing for real, unnoticed — exactly
the risk the auth migration would repeat.

**Two traps in the restore path:**
1. `/api/restore` does **not** snapshot before restoring — it's one-way.
2. `faiz ahmed__backup` currently holds the **abandoned 50-day plan**, so restoring today
   would replace the live 40-day plan with a stale one, permanently.
3. `grep '/api/restore' public/app.js` → **zero hits**. The undo exists and is unreachable.

## 6. Dashboard / account UX — the recommendation

Mobbin blocks automated access (403), so the research came from Google Play, Apple HIG,
Material 3 and design-research sources instead; conventions cited in the agent's report.

**Recommended: a topbar initial-avatar opening an Account bottom sheet, and delete
`.dash-footer` entirely.** Net change to the dashboard body: minus three controls, zero
added. It reuses `.sheet`/`.sheet-scrim` verbatim (already safe-area aware, already
transform+opacity only, already reduced-motion covered), needs no new view and no history
handling, and is where a Google email/photo would later live.

**Real defects it fixes:**
- "Start over" (deletes the plan) sits in a shared flex row with "Sign out", identically
  styled, and `justify-content: space-between` + `flex-wrap` means **its position moves**
  depending on whether "Study reminders" is shown (it's hidden outside the installed app).
- Both confirmations are `window.confirm()`, which in a TWA renders as a Chrome dialog
  prefixed with the origin — the loudest "this is a website" moment in an app that went
  to real lengths to hide that.
- Sign-out is **unconfirmed** while there is no password reset, so it is arguably the
  more dangerous of the two buttons. The risk ranking on that row is inverted.
- `allDone` never reaches the Today card: a completed plan still shows the last day's
  title, its already-earned XP, and a live "Start today". The fix doubles as the
  *positive* route to a new plan, which is what most people reaching for "Start over"
  actually want.
- `#app` bottom padding is a flat `80px` and ignores `env(safe-area-inset-bottom)` —
  every fixed element handles it, but the scroll container doesn't.
- No account-deletion path exists; Play has required one since April 2024 for apps with
  in-app account creation. Reserve the slot.

**Explicitly NOT to do:** bottom nav, a settings *view*, type-to-confirm, red "Sign out"
(destructive styling is for actions the user didn't deliberately choose), a filled red
CTA, animated/badged avatar, a second accent colour, reordering anything above the Today
card.

## 6b. APPROVED, NOT YET BUILT — learner class should change project COUNT

Faiz approved this on 26 Jul. Today `profile.class` reaches only the **lesson**,
**project-brief** and **ask** prompts — so Builder gets more hands-on *lessons*, but
every class gets the **identical number of milestone projects**, because projects are
placed structurally by `_wants_project()` and the class is never consulted.

**Spec.** Pass the class into project placement and let it shift the threshold:

- `builder` → more projects: allow a phase to carry one when it keeps **>= 1** teaching
  day (instead of 2), and consider allowing the first phase past day 3.
- `challenger` → same count as now, but harder briefs (already handled by the brief prompt).
- `scholar` → fewer: require **>= 3** teaching days, so theory-heavy phases stay theory.
- `consistent` → fewer/smaller: require >= 3 too; smaller scope in the brief.
- `allrounder` → today's behaviour, unchanged (the default, so most users see no change).

**Where:** `_wants_project(idx, phase, days, is_last)` in `app.py` gains a `cls`
argument, read from `state["profile"]["class"]`; both call sites (sequential AND parallel
generation) must pass it — they are required to stay in step. `plan_init` already stores
the class before generation runs, so it's available.

**Watch out:** (a) don't let `builder` put a project on a phase with zero teaching days;
(b) the class can be changed later in principle but the curriculum is generated once, so
this only affects NEW plans — say so in the UI if it ever becomes editable; (c) keep the
"never the first phase, never within the first 3 days" guard for every class — a beginner
still can't build on day 2.

**Faiz's decision still owed on Google sign-in.** Plain version: it works, but right now
he stays logged in for a year, so the "forgot password" problem he wants solved hasn't
actually happened. Going Google swaps a failure HE can fix (reset from his laptop) for

outage, blocked Wi-Fi) — each of which would lock him out of his study plan mid-bootcamp.

passwords — conditions in §4.

**Do not bundle these.** The red team's strongest point: six unverified commits landing
together after a week of downtime is already the maximum sensible batch, and a phone has
no devtools to bisect with.
